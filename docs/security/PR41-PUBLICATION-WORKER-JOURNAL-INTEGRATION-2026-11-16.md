# PR41 — Publication journal bridge for the runtime-effective Komodo worker

**Status: code candidate, disabled by default, not deployed.** This extends PR40, which extends PR38. It is not proof of permission to deploy or readiness to promote Hn→Pn. All tests use an isolated SQLite database and simulated Docker calls.

## Changes

`components/runtime/current-apps/komodo-agent-current/cloudif_publication_effect_gate.py` provides an opt-in pre-external-effect bridge to the PR40 `PublicationRecoveryJournal`. The two **runtime-effective** methods `cloudif_publication_release` and `cloudif_publication_release_activate` now enclose the mutating section in the gate; old duplicate definitions earlier in `cloudif-komodo-agent.py` remain older snapshots and are not changed here.

- `CLOUDIF_PUBLICATION_JOURNAL_MODE=disabled` is the **existing compatibility mode**. It does **not** provide durable journaling, and is not proof the release is secure.
- `CLOUDIF_PUBLICATION_JOURNAL_MODE=strict` requires an approved private DB path, a trusted lock directory, an authenticated evidence provider and an evidence verifier **before any external write**. Unknown modes fail closed. The default is `disabled` to avoid unreviewed production changes.
- `CLOUDIF_PUBLICATION_JOURNAL_DB` and `CLOUDIF_PUBLICATION_JOURNAL_LOCK_DIR` must resolve to an operator-provisioned private state volume (e.g. an approved `0700` directory) with the correct service UID, no untrusted writable parent or symlinks, stable storage and backup/restore instructions. The code does **not create or authorize** these production paths.
- A local `fcntl.flock(LOCK_EX|LOCK_NB)` on a validated `0600` regular file keyed by the **global public number** fences concurrent requests on one host. The PR40 SQLite journal also has unique unresolved-operation indexes by project and `public_number`, so an interrupted worker keeps its project/public alias blocked after its process lock releases. **This is NOT a distributed lock across different Docker/Komodo hosts**: an owner-approved lease implementation covering all writers is mandatory before use in a multi-host release.
- The journal transaction for phase `mutating` is committed before environment file replacement, `docker restart`, alias transfer, previous-production stop and SQLite release writes. Early returns, exceptions, failed compensation, evidence verification errors or process death leave a pending `mutating`/`needs_reconciliation` phase, rather than silently accepting a new release. The gate has no automatic replay, remote Docker mutation or secret access.
- On the successful runtime code path the worker requests a SHA-256 reference from a **trusted internal** `_CLOUDIF_V145_EVIDENCE_PROVIDER`, then the PR40 journal requires `_CLOUDIF_V145_EVIDENCE_VERIFIER` to approve the exact operation identity and target phase, and only then marks it `committed` and emits success. **These functions are intentionally not supplied by this PR**, and MUST NOT be loaded from HTTP request bodies, environment text, unverified Forgejo content or client-controlled Python modules.
- When strict mode cannot provision the lock or trusted evidence provider, the handler returns a generic 503 `publication_journal_or_runtime_blocked`, without executing mutations. Missing trusted evidence on an already modified runtime leaves a pending operation requiring owner-led recovery. This may intentionally reduce availability during a failed release.

## Safe production integration prerequisites

1. G0 owner confirms identity, stable service UID, exclusive change lock, all participating mutators, host topology and change scope. Ensure the runtime release package actually contains the two bridge modules adjacent to the active worker and Python can import them. Verify exact Git commit matches active Forja file, not just repository HEAD.
2. G1 current tenant PostgreSQL **and volume** backup archive manifests verified by their authorized owners with an actual isolated restore and rollback proof; do not loosen mode `0700` of backups or reveal archive contents.
3. G2 production OpenBao/broker issues ephemeral, scoped and audited `secret_ref`, authenticated verifier and evidence authority bound to both the exact Docker network alias/container ID/image ID and SQL release identity/status/digest. A SHA-256 string by itself is not proof. Protect verification against time-of-check/time-of-use changes and unverifiable network options.
4. G3 authorized disposable Docker/SQLite test: W1 linked to canonical Forgejo, Hn immutable snapshot, Pn same container ID, previous Pn stopped, effective runtime environment confirmed **inside** container, aliases/static IP/health, first Pn, manual activation, multi-worker contention, process crash after journal intent and after alias switch, ambiguous SQLite COMMIT and audited reconciliation/recovery. Exercise both success and failclosed cases.
5. G4 fix and rotate/revoke the confirmed P0 **22 Git `.git/config` files with embedded credentials** using a change-controlled secret broker; G5 independently verify zero credential-bearing origins and review rollout. No undisclosed URL/token values may enter logs, Git, HTTP replies or this document.
6. After an incident, **do not simply clear the journal row**. A trusted operator must collect DB and Docker ID/image/alias/health evidence, assess compensating rollback, and supply an authenticated proof to an approved reconciler. This PR does not implement that reconciler. Restoring availability without evidence risks duplicate or stale production routes.

### Residual concerns for aud-01 / infra-01 / dev-02

The helper is only enabled via a process-level flag. Unless all aliases are mutated by cooperating workers, a host-local lock and a SQLite unique index do not prevent an out-of-band Docker CLI/Komodo write. The gate conservatively retains pending records even for early failures before Docker effects, requiring manual reconciliation. Deployment packaging must load the bridge module safely, use a private state directory, and provide a trusted verification identity. PR38's alias/network recovery still needs independent Docker proof for static IP, unrelated aliases and crash ambiguity. PR39's Portal ACL/worker authorization remains an independent gate.

The parallel aud-01 sandbox implementation identified the importance of proving the precise ordering of the mutation boundary. Dev-01 added two standalone test cases to PR41: a fake production release asserts that the journal is already `mutating` when the runtime environment file would first be written, and a fake manual reactivation asserts the same before its first `docker start`. ## G3 partial real Docker proof, 16 November 2026 (non-production)

`scripts/dev01-g3-disposable-docker-proof.py` is a deliberately **manual-only** operator test. Its default invocation is read-only, displaying the plan. Actual execution requires explicit `--execute` and the external G0 owner/change-lock authorization; the script additionally refuses wrong host, root identity, high CPU load, low memory or disk, missing local image and name collisions. Do not run it automatically in CI or on a busy production Docker host. It uses an internal no-published-ports network, the already-cached `postgres:15-bookworm` image **without starting PostgreSQL**, two capped sleep containers (64 MiB/0.2 CPU each), a private test-only directory bind, prefix-tagged unique names, no production mounts and `finally` cleanup. The temporary network/containers are verified absent after completion.

Before adding the safe opt-in/resource guards, the same core test was executed **once** via the authorized `cti` Docker access on existing Hospedagem. All six logged stages passed: private network, isolated fixture containers, atomic runtime file replacement visible inside the Hn container after restart, same Docker Hn ID, active alias transferred to Hn, former Pn stopped and complete zero-residue cleanup. Sanitized evidence: LabIFF `evidencias/PGH-DEV01-G3-REAL-DOCKER-PARTIAL-20261116.jsonl`. No real application data or credentials were used. The test does **not** invoke the PR41 journal in Docker, prove distributed fencing, exercise crash/reconciliation against the active worker, verify real W1→Hn→Pn Git provenance or authorize release. Thus **G3 remains partial/blocked**. Subsequent host read-only load at 11:09 UTC was about 9.47 on four CPUs; the guarded script now refuses execution at such load rather than adding pressure.

`portal/tests/test_dev01_g3_disposable_proof.py` tests the read-only-by-default CLI, no-Docker help, CPU refusal, wrong-host/root refusal and static cleanup/resource constraints with no daemon access.

## Crash window AFTER an external effect — additional offline regression, 16 Nov 2026

Two extra tests in `portal/tests/test_dev01_v145_publication_effect_gate.py` now force a **child-only process crash after a durable synthetic external alias change**, not merely after journal intent. The external system is represented only by a tiny fsynced local JSON fixture (NOT actual Docker and NOT production evidence): `mutating` is first committed in SQLite, the external fixture is then durably changed, and the child exits with `os._exit(27)` without running the gate's `__exit__`. A fresh process confirms both that the external effect is visible and that the SQLite journal remains `mutating` despite release of `fcntl.flock`. A retry by the original project and an unrelated project requesting the same global public alias are **both rejected** by the persistent journal indexes.

The second test verifies that a denied proof cannot complete reconciliation and that an explicit, fixture-verified `needs_reconciliation -> reconciled` transition is required before another operation may start. The fixture verifier checks the synthetic alias and operation identity; it is **not** a production identity or attestation provider. This narrows source-test coverage of the crash-after-effect window but **does not** close distributed consistency gaps, prove Docker or SQLite visibility across hosts, or authorize automatic recovery. A real trusted evidence provider and owner-directed recovery remain release blockers.
